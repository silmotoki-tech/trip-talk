# Cursor実装運用ルール

[引き継ぎの入口へ戻る](README.md)

更新日：2026-09-20

## 目的

Trip Talkの日常実装はCursor中心で進める。
ChatGPTで設計・仕様を決め、ChatGPTが**Cursorにそのまま貼れる細かい指示**を作り、Cursorがローカルで実装する。

Cursor側のエージェントには、曖昧な指示や大きすぎる依頼を渡さない。
**推測させない・一度にやらせすぎない・毎回検証する**を基本とする。

### 指示を書く側の前提

ChatGPTはCursorを、長い会話の文脈や設計意図を高精度に補完できる相手として扱わない。
**理解力・文脈保持・仕様補完に限界がある前提で、必要事項を指示文の中に明示する。**

ChatGPT自身が把握している前提でも、Cursorに渡す指示から省略しない。特に似た概念、触ってはいけない既存機能、進捗保存先、対象repo、対象ファイルは明記する。

曖昧さが残る場合は実装させず、先に調査だけさせる。

## 役割分担

- **ChatGPT**：要件整理、設計、仕様確定、Cursor用指示書、差分レビュー
- **Cursor**：ローカルコード編集、検索、修正、lint/build、commit/push
- **ユーザー**：Cursorでフォルダを開く、必要なGUI操作、結果の共有
- **GitHub**：確定仕様・コード・履歴の正本
- **Codex/Work**：大規模移行、一括変更、直接ローカル操作を任せたい場合のみ

## Cursorで作業を始めるとき

ユーザーがTrip TalkフォルダをCursorで開いたら、最初に以下だけ確認する。

1. 対象repoがTrip Talkか
2. branchが `main` か
3. `git status` がcleanか
4. `git pull --ff-only` が必要か
5. `AGENTS.md`、`CLAUDE.md`、今回関係するhandover文書を読む

この確認が終わる前にコードを変更しない。

## 指示の粒度

**1回の指示 = 1つの明確なタスク** を原則とする。

悪い例：
- M2を全部作って
- UIも直してFirebaseも調整してcommitして
- いい感じに整理して

良い例：
- `src/lib/scripts.ts` にMOTOKI0 JSONを読み込む関数だけ追加する
- 台本詳細画面に「答えを見る」ボタンだけ追加する
- Firestore Rulesの `selfRating` 検証だけ修正する

複数工程が必要なら、バグや誤変更の原因を追える程度に分割する。ただし細分化しすぎて往復や作業量が増えないよう、関連が強く一緒に検証した方が安全な変更は1タスクにまとめてよい。

## Cursorへ渡す指示に必ず含める項目

1. **目的**
2. **対象ファイル**
3. **変更内容**
4. **変更してはいけないもの**
5. **実装前に確認すること**
6. **完了条件**
7. **検証コマンド**
8. **作業結果として報告する内容**

## エラーを減らすルール

- 曖昧な「適当に」「いい感じに」「全部直して」を使わない
- 対象ファイルが不明なら、最初は**調査だけ**させる
- 新しい設計をCursor側に考えさせない。設計はChatGPTで先に決める
- 既存仕様と競合したら、勝手に判断せず止めさせる
- 未コミット変更があれば上書きさせない
- `reset --hard`、rebase、force pushは禁止
- 一度に広範囲のrenameや大規模置換をさせない
- 変更後は必ず `git diff` を確認する
- コード変更後は原則 `npm run lint` と `npm run build`
- Next.js 16のAPIを変更する場合は `node_modules/next/dist/docs/` を確認
- commitは検証後に行う
- push前に対象repoとbranchを再確認する

## ChatGPTとの往復方法

1. ユーザーがChatGPTで次にやることを決める
2. ChatGPTがCursor用の短い指示を作る
3. ユーザーがその指示をCursorへ貼る
4. Cursorが実行し、結果を返す
5. ユーザーがCursorの結果をChatGPTへ貼る
6. ChatGPTが内容を確認して、次の1タスクを出す

一度に数段階先まで進めない。

## 大きな機能を作る場合

例えばM2なら、いきなり「M2を実装」ではなく、次のように分ける。

1. 既存schemaと台本配置を調査
2. expression DBの出力schemaだけ実装
3. 1台本から抽出する処理を実装
4. 複数台本集計を実装
5. 重複・再利用ルールを実装
6. 出力ファイル生成
7. lint/build/test
8. commit/push

各ステップが通ってから次へ進む。

## 迷ったとき

Cursorに判断させず、**止めてChatGPTへ戻す**。

特に以下は勝手に決めない。

- schema変更
- Firestore構造変更
- 認証方式変更
- 台本作成方針
- 学習仕様
- データ削除
- 大規模リファクタ
- dependency追加

この運用をTrip Talkの標準開発フローとする。
