# Trip Talk — 視覚シーン練習 / アニメーションモード構想

[引き継ぎの入口へ戻る](README.md)

更新日：2026-09-22

## 位置づけ

Trip Talkでは、現在のテキスト中心の台本練習に加えて、将来的に **視覚シーン練習 / アニメーションモード** を追加する構想がある。

これは単なる装飾ではなく、

**テキストを思い出す → 場面を見たら英語が出る**

へ学習を発展させるための補助レイヤーとして位置づける。

現行の正本である `dialogue` / `expressions` は変更しない。視覚演出は別メタデータとして管理し、英語教材と演出を独立して修正できる構造を維持する。

## 将来の学習フロー

基本の発展形は次のとおり。

1. テキストで予習・反復
2. 質問だけで練習
3. **棒人間アニメ付きで状況想起**
4. ChatGPT Liveで実戦

視覚モードは「質問だけで練習」を、より状況依存の想起へ進化させたものとして考える。

## 基本アイデア

- 全教材で統一した棒人間表現を使う
- リアル人物画像やAI生成画像を教材ごとに作らない
- 1場面につき2〜3コマ程度の粗いコマ送り、または1〜2秒程度の短いループアニメーション
- 滑らかさよりも、少しカクカクした動きで親しみやすさを出す
- 「豪華な映像」ではなく、一目で状況が分かることを優先する
- 発話を邪魔しない

このカクカク感は、教材の堅さを和らげ、Trip Talk独自の視覚的な個性・ブランド要素にもなり得る。

## 想定する最小動作

複雑なアニメーションは不要。以下のような動きを共通部品化する。

- 手招きする
- うなずく
- 指差す
- 紙を差し出す
- お金を渡す
- お金を受け取る
- お金を数える
- 顔や体の向きを少し変える

たとえばCHAMI0の空港両替なら、

1. スタッフがこちらを見て手招き
2. ユーザーがカウンターに近づく
3. スタッフが紙幣や用紙を指差す

程度で十分。

## 目指す学習UI

視覚モードでは、音声はアプリ内に入れない。

基本画面：

- 上部：棒人間・背景・小物による視覚シーン
- 下部：partner側の英語発話
- learner側の返答は初期状態では非表示
- 「答えを見る」で直後のlearner発話を表示
- 「次へ」で次の発話／場面へ進む

文字は最初は**画面下部の固定表示**を基本とする。
吹き出しや中央表示は将来の表現オプションとして検討するが、初回実装では必須にしない。

学習の中心は、

**場面を見る**
→ **相手の英語を読む**
→ **自分の返答を記憶から取り出して声に出す**

である。

learner側の答えを常時表示して、単なる読み上げ練習にはしない。

将来的には、

- Level 1：partner全文表示
- Level 2：partner文を一部省略
- Level 3：文字なし・場面だけ

のように文字依存を減らす発展も検討できる。

## 音声方針

Trip Talkの視覚モードでは**音声再生を実装しない**。

理由：

- TTSや音声ファイル管理を増やさない
- アニメーションとの同期処理を避ける
- iPhone上の挙動とUIを単純に保つ
- Trip Talkは視覚＋文字の想起練習、ChatGPT Liveは実際の音声会話、と役割分担できる

## キャラクター・小物・動き

棒人間は1枚絵ではなく、可能な範囲で再利用できる部品として扱う。

想定部品：

- 頭
- 胴体
- 左右の腕
- 左右の脚
- 服装／名札などの簡単な装飾
- バッグ
- 荷物
- パスポート
- クレジットカード
- ルームキー
- 紙
- お金

共通動作候補：

- point
- nod
- beckon
- small-bow
- hand-passport
- hand-card
- hand-key
- hand-paper
- look-direction

滑らかな動画ではなく、2〜4ポーズ程度の切り替えでもよい。

## 学習上の狙い

主役は映像ではなくユーザーの発話。

基本構造は、

**相手の動き**
→ **partner発話**
→ **ユーザーが発話**

とする。

映像を眺める教材にはしない。視覚刺激を英語発話のトリガーとして使う。

## デザイン方針

AI生成画像は基本的に使わない。

理由：

- 教材ごとに絵柄が変わる
- キャラクターの見た目が安定しない
- 不自然な画像が混ざる可能性がある
- 教材全体の統一感が崩れる
- ファイル容量と管理コストが増えやすい

代わりに、棒人間・背景・小物を共通フォーマットで統一する。

優先するもの：

- 一目で状況が分かる
- 少し和む
- 発話の邪魔をしない
- 全教材で統一感がある

## 実装方針

大量のMP4/GIFを教材ごとに持つ方式は避ける。

優先候補：

- SVG
- 共通画像パーツ
- CSSアニメーション
- JavaScriptによる簡単なポーズ切り替え

共通素材例：

- `person.svg`
- `counter.svg`
- `money.svg`
- `paper.svg`

教材ごとには大きな画像を保存せず、ポーズや表示順だけを指定する方向。

例：

通常姿勢
→ 手を上げる
→ 少し手前に振る
→ 通常姿勢

## 容量の考え方

教材数が増えても重くなりすぎないことを優先する。

目標イメージ：

- 1場面あたり数十KB〜数百KB程度
- 共通SVGや小物を再利用
- 動画ファイルを大量保存しない

厳密な上限値は試作後に決める。

## データ設計

正式な `LearningScript` schema の `dialogue` / `expressions` に視覚演出情報を混ぜない。

英語教材の正本：

- dialogue
- expressions

視覚演出は別管理。

将来の演出メタデータ候補：

- scene背景
- 使用キャラクター
- 使用小物
- pose
- animationType
- loop
- duration

必要なら台本IDなどで紐づける。

## 初回試作

最初から大規模システムにしない。

**初回の実装対象は MOTOKI0「ホテル到着〜チェックイン」** とする。

理由：

- ホテル入口 → フロント → パスポート → デポジット → 館内案内 → キー受け取り、と視覚的な変化が多い
- 荷物、パスポート、カード、キーなど小物表現を試せる
- 指差し、受け渡し、会釈、うなずきなど共通動作をまとめて検証できる
- 現行の正式台本をそのまま使って学習効果を評価できる

最初からMOTOKI0全体を完成させない。
**最初は2〜3場面だけのプロトタイプ**を作り、操作感と学習効果を確認してから広げる。

初期候補：

1. ホテル入口でベルスタッフが荷物を案内
2. フロントでパスポートを求められる
3. デポジットでカードを求められる

良ければ、館内案内・チェックアウト確認・キー受け取りへ拡張する。

## 実装の進め方

実装はCursor / Grok側で一度に大きく進めない。

原則：

1. **調査**
   - 対象repo・branch・git status・origin/mainとの差分を確認
   - 視覚モード追加に関係する既存ファイルを特定
   - この段階ではコード変更しない
2. **入口だけ追加**
   - 既存台本詳細に「視覚シーン練習」への入口を最小追加
3. **空の視覚モード画面**
   - 既存機能を壊さず、表示・戻る導線だけ確認
4. **MOTOKI0の仮データ表示**
   - partner英文とlearner答え表示の基本挙動を作る
5. **静止した棒人間・背景・小物**
6. **答えを見る／次へ**
7. **小さなアニメーション**
8. **MOTOKI0の2〜3場面で実機評価**
9. 問題がなければMOTOKI0全体へ拡張
10. その後に共通部品化・他台本対応

Cursor / Grokへの指示は**1回につき原則1タスク**とし、対象ファイル・変更内容・禁止事項・完了条件・検証を明記する。

最初から汎用アニメーションエンジンを作らない。
まずMOTOKI0で成立する最小版を作り、必要になったものだけ共通化する。

## 台本作成プロジェクトとの役割分担

現時点では、台本作成プロジェクトの正式出力仕様にvisual metadataをまだ組み込まない。

まずMOTOKI0の試作で、

- どのvisual metadataが本当に必要か
- 1場面と1発話の対応をどうするか
- どの動作を共通部品化するか
- どの小物情報が必要か

を確認する。

試作後に仕様を固定し、その時点で台本作成プロジェクトへ、

- 背景
- 登場人物
- 小物
- partner action
- learner action
- text placement
- visual step

などの演出設計出力を追加するか判断する。

## 実装タイミング

**実装準備フェーズへ移行する。**

通常練習フローとMOTOKI0 / CHAMI0が利用可能になったため、MOTOKI0を使って視覚モードの最小プロトタイプを段階的に実装する。

ただし、既存機能を壊さないことを最優先し、上記のスモールステップを守る。

## 守ること

- 映像を豪華にしすぎない
- 画像生成を教材制作の必須工程にしない
- dialogue / expressionsを壊さない
- 視覚演出のために学習仕様を複雑化しない
- 動画ファイル中心の重い構成にしない
- まず1場面だけ試作し、学習効果と操作感を確認してから拡張する
