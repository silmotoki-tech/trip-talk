## 現在の方針

Trip Talkは、**ChatGPTで戦略会議・台本設計 → Trip Talkで予習・反復 → 外部のChatGPT Liveで実戦練習／台本読み上げ**を行う方式で進める。Liveの課題は自動で次台本へ注入せず、同じ台本を反復するか次へ進むかを本人が決める。

アプリ内Realtime API＋Firebaseを中心に据える旧ロードマップは現行方針ではない。再開する場合は別途明示的な意思決定が必要。

## 開発ツール運用

通常の開発フローは次を基本とする。

1. ChatGPTで要件整理・設計・仕様確定
2. ChatGPTがCursor向けの具体的な実装指示を作成
3. Cursorでローカル実装・検索・修正・lint/build。**一度に大きな作業を投げず、1タスクずつ細かく実行する**
4. Firebase Console等のGUI設定はユーザーが手順に沿って実施
5. GitHubへcommit/pushし、必要に応じてChatGPTが差分をレビュー

Codex/Workは、複数ファイルにまたがる大規模移行、一括変更、ローカル操作を直接任せたい場合に限定して使う。

Cursor運用の詳細は `cursor-workflow.md` を正本とする。

## 再開手順

1. `AGENTS.md`、`CLAUDE.md`、`docs/handover/README.md` を確認する。
2. GitHubの対象が `silmotoki-tech/trip-talk` であることを確認する。
3. 最新HEAD、未コミット変更、公開状態を確認する。
4. `script-design.md` の学習思想を確認する。
5. **M0から順番に進める。**
6. コード変更後は `npm run lint` と `npm run build` を実施する。
7. 完了した変更、検証、未検証、コミットSHAを記録する。

## M0 — 旧教材を外し、新しい正本構造を作る

### 目的

現在コード内にある既存ホテル／空港シーン、旧会話例、旧語彙を新教材へ引き継がず、Trip Talkの「器」だけを残す。

### 削除・廃止対象

- 現在のホテル／空港の既存教材
- 既存 `story`
- 既存 `preview`
- 既存 `reactions`
- 既存 `vocabulary`
- 旧教材を前提にした表示・説明文
- Realtime API／Firebase中心の現行ロードマップ扱い

※履歴として残す文書は削除しなくてよいが、過去案であることを明確にする。

### 残すもの

- Next.js / React / TypeScript
- GitHub Pages公開
- 利用者切替
- 予習・反復用UIの基本構造
- ChatGPTを開く導線
- localStorageの設定保存
- 既存内部IDなど、互換性のため必要な技術要素

### 利用者名

- タモやん
- ちゃみ

既存の内部ID `gonzaemon` は、保存キー互換性のため必要なら維持する。ユーザーに見える表示は「ちゃみ」で統一する。

### 新教材の開始

新教材は **MOTOKI0 → MOTOKI1 → MOTOKI2 ...** の順で作る。
既存教材をMOTOKI0として流用しない。

### 新しいデータ方針

教材データとアプリコードを分離する。

方向性：

```
data/
  users/
  scripts/
    motoki/
    chami/
  generated/
    expression-db.json
```

実際のパス・形式はNext.js静的exportとの相性を確認したうえで最小安全変更にする。

原則：

- 確定台本が正本
- 横断表現DBは台本から再生成できる派生データ
- DBをAIが手作業で直接編集する方式にしない

### M0完了条件

- 旧教材が新教材として表示されない
- 新教材を追加できる空の構造がある
- タモやん／ちゃみの利用者区別が維持される
- アプリがbuild可能
- lint成功
- 旧API/Firebase構想が現行方針と誤読されない

## M1 — 新しい台本スキーマを確定

MOTOKI0を作る前に、新台本1本が何を保持するかを確定する。

### 学習単位と進捗

- **1台本＝1学習単位**
- 台本本文は共有教材としてタモやん／ちゃみ双方から閲覧可能
- 練習状態はユーザー別に保持する
- 各ユーザーごとに保持するのは、少なくとも **音読回数・最終音読日時・4段階自己評価**
- これらの個人進捗は **Firebase/Firestoreを正本** とする。SafariのlocalStorageだけには依存しない
- 音読カウンターは台本画面からいつでも押せる。1回音読するごとに手動で+1
- カウンターを押した時刻を最終音読日時として更新する
- 自己評価はいつでも本人が変更可能。評価が高くても台本を一覧から消さない
- 台本を後から修正しても、過去の音読回数・日時・自己評価はリセットしない
- Liveの詳細失敗ログや細かな弱点分析はMVPでは保存しない
- GitHubは教材・台本の正本、Firestoreは個人進捗の正本と役割を分ける

### 質問だけで練習

M1から実装する。

- 台本詳細画面に **「全文を見る」** と **「質問だけで練習」** を用意する
- 「質問だけで練習」では、`dialogue` のpartner発話だけを1つずつ表示する
- ユーザーは自分の返答を声に出してから **「次へ」** を押す
- 必要なときだけ **「答えを見る」** で直後のlearner発話を確認する
- 周回数・正誤・回答履歴はMVPでは保存しない
- 新しい教材データは作らず、既存 `dialogue` を再利用する

### 台本一覧の見せ方

- 基本は**フラットな一覧**
- 各台本に **場面ラベル＋短いサマリー** を表示する
- 場面情報はデータとして持つが、深いフォルダー階層をUIの中心にはしない
- 一覧上で音読回数・最終音読日時・自己評価を見えるようにする

候補：

- id
- learner
- scene / situation
- goal
- dialogue
- key expressions
- vocabulary
- questions
- reactions
- repair / clarification expressions
- reused expressions
- new expressions
- tags / metadata

必要最小限に絞り、将来の横断表現DBを再生成できる形にする。

## M4 — 練習UI強化

データ構造が固まってから必要に応じて追加する。

### 読み上げモード

各台本に **「読み上げ用指示書を作る」** ボタンを用意する。

目的：
- ChatGPT Liveに台本をそのまま読み上げてもらい、ヒアリング練習に使う
- 電車・待合室など、自分が発話できない場所でも学習できるようにする

原則：
- 通常のロールプレイとは別モード
- 台本の質問→答え→質問→答えを順番どおり読む
- 内容を改変・要約・追加しない
- ユーザーへ質問して返答を待つ会話モードにしない
- 台本を最後まで読み切ったら終了する
- 読み上げは原則 **1回ずつ** 実行する
- 最初の読み上げ用指示書に、**ユーザーがLive内で「もう一回」と言ったら同じ台本を同じルールで最初から最後まで再読する**ことをあらかじめ含める
- 反復時はTrip Talkへ戻って指示書を再生成しない。ユーザーがLive内で「もう一回」と言うだけでよい
- 複数回を一括指定するより、1回ずつの再読を優先する
- Trip Talk自身は音声再生しない。Realtime API、音声API、ブラウザTTSを使わない
- 読み上げ速度などの細部は実装時に必要最小限で決める

- 自分から質問する練習
- リアクション
- 聞き返し
- 確認
- 言い換え
- 既習表現の自然な再登場

UIを先に大改修しない。

## 学習ルール

- 台本／会話例による反復が中心
- ChatGPT Liveは反復後の実戦練習
- 本人が反復／拡張／場面変更を決める
- 相手の質問に答えるだけでなく、自分から質問する力を鍛える
- リアクション、聞き返し、確認、言い換えも学習対象
- アメリカ英語を基準とし、国際英語環境で通じることを優先
- 既習表現を自然に再利用し、新規表現を増やしすぎない
- 台本数は先に固定せず、獲得目標から逆算する

## 避けること

- Tamoyan-Englishの構造や仕様をTrip Talkへ持ち込む
- API/Firebase/Realtimeを勝手に中心機能へ戻す
- AIが自動進級・卒業判定する
- 台本を過去データ参照なしで大量自動生成する
- 既存設定キーを不用意に改名する
- `localStorage.clear()` 等で全消去する
- 公開GitHubへ秘密情報や個人会話ログを保存する
