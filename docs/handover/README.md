# Trip Talk — 開発引き継ぎの入口

更新日：2026-09-20

## 最初にここだけ読む

### 最重要：Cursor向け指示は「理解力・文脈保持に限界がある」前提で書く

Trip Talkでは、ChatGPTが作った指示をユーザーがそのままCursorへ貼って実装させる。
そのためChatGPTは、**Cursorが高い文脈理解・推論・仕様補完をしてくれる前提で指示を書いてはいけない。**

Cursor向け指示は必ず次を満たす。

- 1回につき原則1タスクだけにする
- 目的、対象ファイル、変更内容、変更禁止事項、完了条件、検証方法を明記する
- 似ている概念がある場合は「何と何を混同してはいけないか」を明記する
- 既存仕様との関係を必要な範囲で書き、推測させない
- 対象ファイルや既存実装が不明な場合は、いきなり実装させず最初に調査だけさせる
- 大きな変更は、バグの切り分けができる程度に適度な単位へ分割する。細かく分けること自体を目的にせず、関連が強く一緒に確認した方が安全な変更はまとめてよい
- 「いい感じに」「適切に」「既存に合わせて」など、Cursor側の判断に依存する曖昧表現を避ける
- Cursorの報告をChatGPTが確認してから次の指示へ進む。数段階先まで一度に指示しない

**ChatGPT側が仕様を理解していても、その理解がCursorへ自動的に伝わるとは考えない。必要な前提は毎回の指示書に明示する。**

### 最重要：学習者と教材対象を混同しない

Trip Talkでは、次の2つは**完全に別の概念**として扱う。

- **現在の学習者**：いま誰の進捗として練習するか。内部IDは `tamoyan` / `gonzaemon`。音読回数、最終音読日時、自己評価などのFirestore進捗の読込・保存先を決める。
- **教材対象**：その台本が誰向けに設計されたか。台本の `targetUserId` と、`MOTOKI...` / `CHAMI...` のIDで識別する。これは教材一覧の表示・絞り込みに使ってよいが、進捗保存先を変更してはいけない。

例：**ちゃみがMOTOKI0を練習した場合、教材対象はタモやんでも、進捗はちゃみ側 `progress/gonzaemon/scripts/MOTOKI0` に保存する。**

双方とも全教材を閲覧・練習できる。この共有仕様を壊してはいけない。

実装時は、既存の「学習者切り替え」を教材フィルターとして安易に流用しない。教材対象の切り替えUIを追加する場合は、学習者stateとは別stateとして設計し、Firestore進捗の読込・保存ロジックに影響しないことを確認する。

現在のTrip Talkは、**台本／会話例を使った予習と反復を中心にし、その後ChatGPT Liveで実戦練習する**旅行英会話アプリとして再設計中。

重要：アプリ内Realtime APIを中心機能にする方針ではない。ChatGPT Liveは外部のChatGPT機能として使う。API＋FirebaseでLive・分析・履歴保存を完結する過去構想は、現行方針ではない。

### 現在の決定

- 台本設計はChatGPTの専用プロジェクトで行う。
- 「台本作成」では、過去データ確認 → 戦略会議 → 設計整理 → 台本作成の順で進める。
- Trip Talkは確定した教材の保存・予習・反復・Liveへの導線を担う。
- 現在コード内にあるホテル／空港の既存シーン・会話例・語彙は、新教材へ引き継がない。M0で削除対象。
- 新教材は **MOTOKI0 から順番に作る**。台本数は先に固定しない。
- 2人の表示名は **タモやん** と **ちゃみ**。既存互換性のため内部ID `gonzaemon` は必要なら維持する。
- 教材データはアプリコードから分離し、確定台本を正本としてGitHubへ蓄積する方向。
- 音読回数・最終音読日時・4段階自己評価などの個人進捗はFirebase/Firestoreへ保存する。これはLive/分析用ではなく、Safariのデータ消去でも進捗を失わないための永続保存用途。
- 利用端末は **iPhone専用** を前提とする。タモヤンポータルから通常のページ遷移でTrip Talkを開く。iframe埋め込みを前提にしない。
- 各台本には **ChatGPT Live読み上げ用の指示書生成** を用意する。Trip Talk自身は音声を再生せず、API/TTSも使わない。
- M1から **「質問だけで練習」** を実装する。相手の発話だけを1つずつ表示し、自分で返答してから「次へ」、必要なときだけ「答えを見る」で回答例を確認する。
- 読み上げ開始時の指示書に「私が『もう一回』と言ったら、同じ台本を同じルールで最初から最後まで再読する」を含める。以後はLive内でユーザーが「もう一回」と言うだけで再読し、Trip Talk側で指示書を再生成する必要はない。
- 将来的に台本から横断表現DBを再生成し、次の台本作成で最新の既習表現を参照する。
- AIが自動で進級・卒業を決めない。反復／拡張／場面変更は本人が選ぶ。

## 作業中に守ること

- GitHubへ書き込む前に対象が `silmotoki-tech/trip-talk` であることを確認する。
- Trip TalkとTamoyan-English、management-theme-appを混同しない。
- コード変更前に `AGENTS.md` / `CLAUDE.md` を確認する。
- Next.js 16系のコード変更では、必要に応じて `node_modules/next/dist/docs/` の該当資料を確認する。
- 本人が難易度と進行を選ぶ。AIの自動進級を追加しない。
- Realtime APIやアプリ内Liveの導入を勝手に再開しない。Firebase/Firestoreは個人進捗の永続保存用途に限定する。
- 秘密情報、個人の会話原文、端末の学習履歴を公開GitHubへ保存しない。
- 既存設定キーや未コミット変更を壊さない。テスト片付けで全消去しない。
- 実装後は `npm run lint` と `npm run build` を確認する。
- 日常の実装作業は **Cursor中心** とする。ChatGPTは設計・仕様整理・レビュー・Cursorへ渡す指示書作成を担当し、Firebase Console等のGUI設定はユーザーが手順に沿って実施する。Codex/Workは大規模移行・複数ファイル一括作業・ローカル操作を直接任せたい場合に限定して使う。
- Cursorでは、一度に大きな指示を出さず、**1タスクずつ・対象ファイル・変更内容・禁止事項・検証コマンドを明示**する。Cursor側のエージェントが誤解しやすい前提で、推測させず、変更前後の確認を細かく挟む。

更新時は、現在の決定と過去構想を混ぜず、現行方針を明示する。
